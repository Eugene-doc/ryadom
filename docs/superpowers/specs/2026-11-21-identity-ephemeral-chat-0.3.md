# 0.3: идентичность устройств и эфемерный чат — спецификация

**Дата:** 21.11.2026  
**Статус:** проект, требует подтверждения перед реализацией  
**Связано:** [docs/ROADMAP.md](../ROADMAP.md), раздел 0.3 и пункт 1.1

## 1. Продуктовый контракт

- В каждый момент времени существует **один главный** и **одна эфемерная сессия чата**.
- Все подключённые устройства видят одну и ту же историю текущей сессии.
- История принадлежит **сессии главного**, а не устройству:
  - при штатном выключении главного или полном выходе из чата история очищается на всех устройствах;
  - при аварийном завершении остатки очищаются до открытия нового сетевого listener;
  - при смене главного предыдущая сессия завершается, следующий главный начинает новую пустую сессию.
- Сообщения, вложения и tombstones **не реплицируются** между главными. Реплицируется только управляющий слой: идентичности, trust roster, term/сессия и handoff.
- Настройки, TLS-сертификат, identity-ключ, доверенные устройства и отозванные устройства сохраняются при очистке истории.
- IP-адрес — временный маршрут, не идентичность. Главный запоминается по `hostDeviceId` + identity fingerprint; адрес обновляется при discovery/переподключении.

## 2. Граница с разделом 1.1

Пункт **1.1 «Постоянная идентичность главного»** полностью входит в 0.3: это сетевая половина модели `deviceId`/fingerprint. В 0.3 реализуется он, но **не** остальные пункты 1.1:

- не делаем отдельно шифрование локального ключа сверх минимума, требуемого identity;
- не делаем глобальные лимиты, диагностику, целостность бинарника, Android sleep/restart, Windows performance, Android SQLite.

## 3. Идентичность

### Устройство

- Один раз создаётся ключевая пара; `deviceId = "d1-" + base64url(SHA-256(SPKI))`.
- Приватный ключ не покидает платформенное хранилище:
  - Windows — CNG/DPAPI, файл с ACL текущего пользователя;
  - Android — Android Keystore.
- Имя и роль не входят в `deviceId`.
- Переустановка/удаление данных создаёт новую личность; автоматическое «восстановление» по имени/IP запрещено.
- Pairing делает UPSERT по `deviceId`; тот же ID с другим ключом — отказ.

### Главный

- Главный публикует `hostDeviceId`, `identityFingerprint`, `tlsFingerprint` и подписанную TLS-binding.
- TLS-сертификат — отдельный транспортный ключ; его смена допускается только с валидной подписью identity-ключа.
- Клиент хранит host identity, а адреса — как подсказки.

## 4. Control plane

```
groupId
rosterRevision
rosterHeadHash
trustedDevices[]
trustOperations[]
lastAcceptedTerm
lastHostId
```

- Каждая операция реестра подписана, содержит `revision`, `previousHash`, тип, субъект и подпись.
- Клиенты синхронизируют журнал через `/api/trust/sync?after=N`, проверяют хеш-цепочку и подпись.
- Реестр — килобайты; сообщения/файлы в него не входят.
- Бывший клиент, став главным, уже имеет roster и может проверять знакомые устройства.
- Роль `host` вычисляется динамически; она не хранится как часть личности.

## 5. Сессия и очистка

- `sessionId` — случайный ID каждого запуска главного; `revision/deletionRevision/epoch` действуют только внутри сессии.
- Каждое сообщение, файл, событие и операция несут `sessionId`.
- Хранилище:
  - постоянное: identity, TLS, settings, trust roster, known hosts;
  - эфемерное: `sessions/<sessionId>/chat.*`, `files/`.
- Штатное завершение:
  1. `ACTIVE → ENDING`;
  2. запрет новых сообщений/загрузок;
  3. отмена и ожидание загрузок;
  4. SSE `session_ending`;
  5. закрытие listener/SSE/БД;
  6. атомарное переименование каталога в `.deleting-*`;
  7. удаление;
  8. удаление crash marker только после успеха.
- Crash marker создаётся и fsync-ится до listener. При старте остатки удаляются до открытия порта.
- Клиент, пропустивший SSE, очищает историю при смене `sessionId` в `/api/state`.
- Закрытие клиента не очищает общий чат; очищает только завершение текущего главного.

## 6. Смена главного

- Только явная целевая передача (targeted handoff), без автоматического failover.
- Handoff подписан, содержит `groupId`, `from`, `to`, `oldSessionId`, `nextTerm`, `rosterHeadHash`, `nonce`, `expires`.
- После handoff старый главный очищает сессию; новый начинает пустую.
- При split-brain без кворума возможны два кандидата; 0.3 не обещает автоматическое разрешение. Для двух устройств безопасный кворумный takeover не гарантируется.

## 7. Протокол 4

- `PROTOCOL=4`; v3-клиенты получают update-required и не допускаются к auth/pairing.
- Новые API: `/api/identity`, `/api/auth/challenge`, `/api/auth`, `/api/trust/sync`, `/api/session/end`, `/api/host/handoff/prepare|accept`.
- `/api/state` добавляет `group` и `chat.sessionId/term/hostDeviceId`.
- SSE получает `sessionId`; новые события `session_ending`, `session_ended`, `trust_changed`, `host_handoff`.
- Discovery V2 возвращает protocol, groupId, hostDeviceId, fingerprint, TLS fingerprint, sessionId, term, rosterHeadHash и подпись.

## 8. Что не входит

- Репликация истории/файлов между главными.
- Автоматический failover и кворум.
- iOS.
- Остальные пункты 1.1.
- Гарантия стирания копий, которые пользователь уже сохранил вне Рядом.

## 9. Критерии готовности

- Смена IP не создаёт новое устройство и не требует pairing.
- Один ID во всех ролях; тот же ключ после смены роли не создаёт дубль.
- Подмена ключа/ID отклоняется.
- Штатное выключение главного очищает историю у всех; crash-recovery очищает до listener.
- Новый главный начинает пустую сессию; старые SSE/сообщения игнорируются.
- Revoke и roster переживают смену главного.
- v3-клиент не подключается к v4.
- Node/Android/Windows тесты и ручная матрица зелёные.
